# Choices

Decisions made while building Auralis, and why.

| Choice | Why | Revisit when |
| --- | --- | --- |
| **One Node server for static files, API and WebSocket** | Simplest thing that runs anywhere a Node process can. No extra services to deploy. | Traffic needs horizontal scaling (then share house state through Postgres or a pub/sub). |
| **Server-authoritative game, client sends intents** | Coins and furniture can't be faked from the browser; every rule is checked in one place. | Never; keep it. |
| **Rules in `shared/*.js`, used by both sides** | One source of truth for layout, placement and stats; the client can preview exactly what the server will accept. | — |
| **Canvas with art drawn in code** | No asset pipeline, every sprite is recolourable, and everything is original. | Hiring an artist (sprites can move to sheets without changing game logic). |
| **Whole-number scaling, smoothing off** | Pixel art stays crisp on every screen. | — |
| **World in memory, saved as JSON rows** | Fast reads; a small, readable schema; easy to evolve (new fields need no migration). | Hundreds of active players (then save only changed rows — done; chat and sessions already live outside the row). |
| **Neon Postgres in production, SQLite locally** | Neon survives host restarts and branches for previews; SQLite keeps local development and tests offline and dependency-free. | — |
| **`pg` connection pool on the pooled `DATABASE_URL`** | Neon's recommendation for a long-running Node server; TLS is pinned to `verify-full`. | Moving to serverless functions (then the Neon serverless driver). |
| **Own accounts: username + scrypt + hashed tokens** | Small, no third-party dependency, and fixes the "anyone with your ID is you" problem. | You want password reset, email, "Sign in with Google" or MFA — then Neon Auth (Managed Better Auth). |
| **Public player id separate from the secret token** | Housemates see your id in house state; it must not be a credential. | — |
| **Neon Object Storage via the Files SDK** | Recommended by Neon; branches with the database; the code isn't tied to one storage provider. | — |
| **Snapshots private, shared via 1-hour presigned URLs** | Nothing is public by default; links can be shared without exposing credentials. | Snapshots become public profile images (then `public_read` plus a CDN). |
| **Pets wander deterministically** | Every viewer sees the same pet in the same spot with zero network traffic. | Pets need to react to players (then simulate on the server). |
| **Standing still is a local toggle** | Tapping your own character sets a client-side `staying` flag that `wander()` checks, so standing still costs no new message, field or save entry; anyone who moves afterwards sends `pos` exactly as before. | Housemates should see a deliberate "away from keyboard" pose (then it becomes a real state on the player row). |
| **Decorate frames the room, not the player** | Decorating is about a room, and your character is free to wander into a housemate's while the panel is open, so the camera follows `editRoom` for as long as Decorate is open and hands control back when it closes. | Several people decorating one room together (then the framed room becomes a shared choice). |
| **Singing is visual only** | The game is a quiet study companion; mic/karaoke sound would fight whatever the player is actually listening to, and a singer's own music lives outside the game. No audio, no new field: `use` already rides on `pos`. | Real karaoke playback (then it becomes an opt-in audio feature, not a pose). |
| **Naps are local, waking is shared** | Where a pet is dozing and how long its sunbath lasts live in the client (`petSeat`, `petSunAt`), like the rest of its wandering. The one thing that must agree is being woken: a `pat` is already broadcast to the house, so clearing the nap there wakes the pet on every screen without a new message. Every nap also has an end time (`until`), so nothing depends on somebody clicking: a pet gets up on its own after four to eight minutes on a chair, or after a sunbath's twenty to forty-five seconds. A pet sofa or pet bed is the exception: clicking it (`pet_sofa`) puts a pet to sleep there (`pet.sofa` on the pet row, saved and rebroadcast), and it only wakes after two pats in a row — the server clears `sofa` then, and every client draws it getting up. That bed is a destination like any other, so the walk there is client-side too: the pet routes to the piece's tile in house coordinates (never its room-local ones, which only line up in the first room) and only curls up on arrival. | Two people watching a chair pet disagree about the exact second it got up (then send a wake message and a timer). |
| **A nap is a slot, so furniture changes carry it** | `pet.sofa` names a piece by its owner, room and index, which is what makes the nap survive a reload without a second id on every piece and lets any member's pet sleep on anyone's bed. The price is that every change to a furniture list has to fix the naps up across the whole house: picking a piece up or swapping one out wakes the pet whose piece left, and a piece that moves to another slot takes its pet with it. Skipping that let a pet sleep on whatever piece inherited the index. | Give pieces stable ids (then the nap needs no remapping but the save and every message grow a field). |
| **Pets react to people from their own local state** | `myBond` and `fav` are the only bond facts a client gets, and the visiting, hanging out, tricks and toasts are all decided in the render loop from them plus positions and the clock. The pet never needs a server-side simulation to look alive, and no bond number is ever exposed. | Each client could disagree about a guest's own visits (then drive them from a server-sent schedule). |
| **Duet and pet reactions are client-side checks** | Where a second mic sits and whether a pet is near enough are both derivable from the room and the clock, like pet wandering. Adding a server field would put a cosmetic on the wire and in the save file. | Pets should react to more than singing (then a small shared table of reactions). |
| **Retro karaoke is a record-player console, no 45 adapter** | The arched jukebox read as a face; the 45 adapter made the deck fussy at 16 px. A plain cream spindle and a chrome tonearm say “record player” with fewer pixels. | Higher-resolution furniture art. |
| **Expensive pets (300–2,000 coins)** | At 1 coin per focused minute, a pet takes real study time to earn. | Players feel the gap is too big (add cheaper pets or coin bonuses). |
| **Selling a room pays its full price back and keeps its furniture** | A room is bought outright, not rented, so taking a cut on the way out would punish someone for changing how many rooms they need. The pieces in it are already paid for, so they return to Storage instead of vanishing — and since they come back as plain catalog items, a custom colour or style is dropped, the same as putting a piece away. | Rooms start carrying decor that should not be refundable (then sell the shell only). |
| **Neighbours share a wall that opens up** | Side-by-side rooms feel like one big home; posts, pillar and a floor seam keep each room recognisable. | Freeform house building. |
| **Turn = mirror flip, not 90° rotation** | Works for every item without drawing each piece from four sides. | Specific items get proper side views. |
| **Two-tap "give up" instead of `confirm()`** | Some browsers and app shells block native dialogs. | — |
| **Fredoka for UI, pixel digits only for the timer** | Pixel fonts made numbers hard to read (5 looked like S). | — |
| **A Guide panel, not more tooltips** | The hover tooltip already names the click; what people miss is the consequence. A tooltip that ran to two sentences would be in the way every time. | Players stop opening the Guide (then surface the two or three lines that matter in the panels themselves). |
| **One nudge per item, remembered per player** | A nudge you have already had is noise. `tipsSeen` is a plain list on the player, and the server is the one that decides which ids are legal. | Players change devices often (then sync it, which `tipsSeen` already does, since it rides in `me`). |
| **Announcements in the bell** | One place for what happened while you were away, and the bell already counted unread things. Posting moved with it, which also fixed a Delete button that never rendered. | Announcements grow long or need editing (then they become their own panel). |
| **Chat thread buttons are rewritten only when what they say changes** | The chat card re-renders twice a second. Replacing the header's markup on every tick put a fresh button under the pointer between mousedown and mouseup, so the browser dropped the click and Unfriend / Leave group did nothing. Writing the same HTML is never needed, and keeping the exact nodes is what makes the click land. | — |

| **Sessions are a log with a day roll-up** | The newest 3000 `{at, minutes, tag}` objects rode on every player row: each finished session rewrote a large row twice (saves only skip unchanged rows, and this one always changed), history was silently truncated at 3000, and the leaderboard summed an array per player. Sessions now append to `sessions` and nothing reads them from a row. Anything older than 90 days folds into `session_days` — one row per player, day and subject — at boot and every six hours, so totals, streaks, subject splits and the year chart stay right while the detail table holds about a term. Rolled-up days are UTC days, and per-hour detail is lost past the window. | Per-hour history older than 90 days matters (then keep the rows and prune with a retention job instead of folding them). |
| **Chat lives in the archive, never in a saved row** | Keeping the last 50 lines on both participants' rows meant one line rewrote a big row twice, boot loaded every conversation of every player, and a 21st private thread silently dropped the oldest. Now `messages` is the only copy and `threads` is a per-member index; a player's conversations are read when they connect (two queries), and the last 50 lines of the threads they can see sit in a bounded cache for `state` to render. `state` shapes did not change, so the client did not either. | Someone asks for server-side search over a player's whole history (then query `messages` directly, not the cache). |
| **A chat line is a frame, not a snapshot** | 438 MB of WebSocket responses in two days on two connections was almost all world re-sent: one snapshot per intent, and one per presence heartbeat, each carrying all rooms, all to-dos and every chat tail. A line is now one `{t:'msg'}` frame to the people who can read that thread, presence and coins have their own frames, the chat tails ride only in a full state (connect, join, a house change, a late thread load), and the socket negotiates `permessage-deflate` for what snapshots remain. | A client that needs the whole conversation on every update (then send a tail revision, not the tails). |
| **A room is a revision, not a payload** | With chat tails out of the ordinary snapshot, `members[].rooms[].furniture` was nearly all of what was left: four furnished rooms put a state at ~3 KB, and every to-do, coin or furniture change paid for all of them. Each room now carries a hash of its content (`server/rooms.js`), a snapshot sends `{ r }` for one the viewer already has, and the per-connection map is forgotten on a new socket so a reload still gets the whole house. Measured with two sockets on a temp database: a to-do snapshot 3154 → 1319 bytes, a one-piece change 3005 → 1643 (one room body instead of four), a connect unchanged at ~3.2 KB. | A client that cannot keep its own copy of a room (then send a full snapshot on every change and accept the size). |
| **The conversation list is its own table** | The newest 50 messages of up to 20 private threads and 20 groups rode on *both* participants' player rows, so a chat line rewrote a large row twice, and a 21st conversation silently dropped the oldest from the row (the archive kept it, the client lost it). `threads` now holds one small row per member per conversation — newest message, `seen`, `muted_until` — and is written alongside the archive, while the text itself lives once, in `messages`. Seeding it from the existing rows means no history is lost on the way in. | Chat history leaves the player rows entirely (the next step: `state` reads its tails from the archive instead). |
| **Message ids resume after the newest message** | Ids were `Date.now()` plus one per process, so a restart started the counter *backwards* and a new message could be issued an id that already existed. The archive inserts with `on conflict do nothing`, so the message vanished, and paging by `id < before` skipped history. The counter now starts at `max(id) + 1` from the database, and Postgres can generate an id itself (`generated by default as identity`, sequence moved past what is stored) so two processes can never hand out the same one. | Full identity ids everywhere (then messages are inserted without an id and read back with `returning id`). |
| **One declarative schema, two small runners** | The DDL used to live in each store, and they drifted: SQLite had `muted_threads`, `chat_themes` and `reset_tokens` tables, Postgres kept the same settings inside the player JSON, and only SQLite had ever been tested. `server/schema.js` now describes every table and index once, renders it per dialect (`jsonb` vs `text`, `bigint` vs `integer`), and records applied migrations in `schema_migrations`; each store only supplies a ~15-line runner. A conformance suite runs the shared interface against SQLite always and Postgres when `TEST_DATABASE_URL` is set, so “it works locally” can no longer mean “it does not work in production”. | A store needs DDL the renderer cannot express (then that migration is written by hand next to its version, not in a store). |
| **A fingerprint per row instead of its saved JSON** | A save has to know what changed. Keeping the last-written JSON of every player and house doubled the world in memory, and building the next diff added a third copy at its peak — which is how a 512 MB instance ran out of heap over ordinary game data. A fingerprint answers "unchanged" in a few bytes, the diff streams in chunks of 40 rows, and the world is the only full copy. | — (done: chat and study sessions live in their own tables). |
| **A readiness check has to touch the database** | `/api/health` used to answer `ok` from a constant, which is a liveness check wearing a readiness check's name: a process whose Neon branch is asleep answered 200 and the host kept sending traffic to a server that could not serve it. The route now runs a trivial query with a 2 s timeout and answers 503 while it fails. | A host that needs separate liveness (then split it into `/livez` and `/readyz`). |
| **One message budget per socket, refilled over time** | Every intent already has its own cooldown, so the missing guard was the one against a script doing something legal a thousand times a second. A token bucket (40 burst, 8 a second) drops the excess and tells the client, instead of closing the socket and making a laggy phone reconnect. | Abuse that spreads over many connections (then a per-account limit too). |
| **Coins can be gifted without a daily cap** | The five-a-day cap was there to stop coins being shovelled between accounts, but a gift only moves coins that already exist: the sender pays exactly what the receiver gets, so there is nothing to farm. The cap only annoyed housemates paying each other back, and its "try again tomorrow" was the first thing anyone hit. The sender's balance is the limit now. | Coins that can be *created* by a gift (then a cap is load-bearing, not cosmetic). |
| **Coalesce chatter in the client, don't widen the budget** | The budget was being spent by ordinary input, not by abuse: one `typing` per keystroke, one `paint`/`look` per colour dragged over in the picker, and one `move` per arrow-key auto-repeat. Raising the token bucket for everyone would have hidden it and slowed down the thing it exists to stop, so each of those now sends one message per *intent* — once per run of typing, once per picked colour, at most every 150 ms per held nudge (the newest queued press is sent when the window expires, so a quick second tap is delayed rather than lost). A dropped intent is invisible apart from the toast, which made a busy typist think the game was broken. | An input that genuinely needs live high-frequency streaming (then a separate, explicit channel, not the intent socket). |
| **Chat history is kept two years** | `messages` is the only thing in the database that grows with every word typed, and nothing read it past the newest page in practice. A daily prune keeps the archive bounded; the day and subject roll-up and `totalMinutes` keep the statistics whole. | Someone asks for a searchable lifetime archive (then an export, not a bigger hot table). |
| **Chat themes get a table** | A colour per conversation was being written into the player JSON on every pick, which rewrote the whole row for a hex string — and Postgres never read it back at all, so themes silently did not survive a restart there. `chat_themes` now holds them in both stores, is read once at boot, and the row stops carrying them. | Per-message theming or shared themes (then the key stops being `(player, thread)`). |
| **Leaderboard totals are cached for 30 s** | The board sums two tables across every player on each request, and the same board is requested by everyone looking at it. A short memo keyed by scope and period, cleared when a session is appended, is enough to stop the sum being the expensive part of a popular screen. | A board that has to be exact the instant a session ends (then drop the TTL). |
| **A finished session is not lost when the write fails** | `addSession` was fire-and-forget: a database blip during `focus_done` lost the session from the log while `totalMinutes` still counted it, so the panel and the leaderboard disagreed. Failed appends are queued and retried, and totals are reconciled from the tables at boot. | — |
| **A stub per player, and a save that skips it** | Parsing every account's JSON at boot is the fixed cost of a restart and the fixed part of the heap, and most accounts are not online. `LAZY_PLAYERS=1` boots with `{ id, name, house, home }` per player and reads the full row when someone connects (plus their house and friends, whose looks and rooms their screen draws). The risk is obvious and is guarded in one place: `changedRows` skips stubs, so an unloaded row can never be written back. | Everyone is online at once (then nothing is saved by it). |
| **A reset link is hashed, single-use, and rides in the URL fragment** | A reset link is a bearer secret for an hour, so it gets the same treatment as a login token: 32 random bytes, only the SHA-256 hash stored, one live link per account. It is spent by the reset it pays for, and that reset also revokes every session, because the reason to reset is usually that somebody else had the password. The token sits after the `#`, which the browser never sends to the server, so it never lands in an access log or a `Referer` header; the client then drops it from the address bar. Its host is the origin the request came from when that origin is one of `ALLOWED_ORIGINS`, so a second domain for the same game (Vercel next to Netlify) mails links that stay on it instead of hopping to the other one; anything not on that list falls back to `SITE_URL`, so a link can never be aimed somewhere we do not serve. | Reset links must survive a mail scanner that visits them (then confirm the reset with a second click on the page). |
| **`/api/forgot` answers the same for every address** | The obvious implementation ("no account with that address") turns a login form into a way to ask who has an account here. So the route always answers `{ ok: true }`, mails only when there is an account, and slows repeat attempts per address; the page says "if that address has an account…" because that is all it knows. | Sign-up starts telling people an address already has an account (it does: the enumeration exists at the other end). |
| **Email goes through an HTTP API, not SMTP** | Render's free plan blocks outbound 25, 465 and 587, and 25 stays blocked on paid (it runs on EC2), so an SMTP client would look correct and deliver nothing. Brevo is the default because it sends from one verified sender address with no domain to configure, which is what a personal inbox needs; Resend is a `MAIL_PROVIDER` switch away once there is a domain. A failed send is logged and swallowed: the person asking for a link is told the same thing either way. | The project gets a domain (then Resend, with `MAIL_PROVIDER=resend`), or mail volume outgrows a free plan. |
| **A stalled socket is dropped, not queued to** | WebSocket `send` never blocks, so a client that stopped reading (a phone that lost signal, a tunnel that died) silently accumulates every broadcast. A 2 MB unread-buffer limit plus a 30 s ping ends that socket; it reconnects and gets a fresh state instead of growing the server's heap. | — |
| **A plush is a tabletop thing, and a bed needs no surface height** | A plush you cannot put on a bed is a plush you have to keep on the floor, so the plushes moved into the `top` layer, which collides only with itself: a bed, a dresser, a rug or the floor all take one, and nothing in the room stops being walkable. They are sorted just in front of the piece they sit on, because a tabletop item used to sort at its own tile and a three-tile bed would swallow it. Tables get a `SURFACE` lift because their art puts the top surface above the tile's lower edge; beds are drawn filling every tile of the footprint, so the honest lift is zero and a bed in that table would only make every plush float over the headboard. | Bed art that leaves a visible gap between the mattress and the tile edge (then it earns a `SURFACE` entry like a table). |
| **The small shark is the big shark's art sampled at half size** | A second hand-drawn shark was a different toy wearing the same colours: a rounder head, an eye the big one does not have, a thinner tail. Sampling `SHARK_ROWS` every other pixel keeps the silhouette, the tail flukes, the dorsal fin, the belly band and the mouth exactly where the big plush has them, in the same palette, so the pair read as one toy in two sizes; the only cost is that its outline is half a room pixel, the same detail every redrawn piece uses. | A shark that needs its own pose (then it is a new item, drawn as one). |

## Known limits

- Pets walk straight between tiles and can pass over furniture.
- All rooms in a house are saved together on each change; fine at friend scale.
- Password reset needs a mailer. Without `MAIL_API_KEY` the link is only logged and the person is told the same "if that address has an account…" — so on a server with no mail configured, a forgotten password cannot actually be recovered.
- The game server must stay running (WebSockets), so it needs a host for long-lived processes (Render, Fly.io, Railway, a VPS), not short serverless functions.
